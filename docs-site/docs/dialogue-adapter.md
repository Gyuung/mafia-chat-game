# 대사 어댑터 내부 계약

v2 작업 D에서 구현한 공급자 중립 대사 준비 계층입니다. 현재 게임 훅에는 연결하지 않았으며 게임은 기존 규칙 기반 대사를 사용합니다. 실제 API·키·모델·네트워크 호출은 포함하지 않습니다. 가짜 공급자는 테스트 폴더에만 있습니다.

## 모듈과 책임

| 파일 | 책임 |
| --- | --- |
| `dialogue/types.ts` | 모델 입력·공급자 인터페이스·결과 타입 |
| `dialogue/context.ts` | 신뢰할 수 있는 게임 상태에서 NPC용 최소 입력 생성 |
| `dialogue/coordinator.ts` | 요청 중복 제거, 시간 제한, 응답 검증, 취소 및 단일 결과 소비 |
| `tests/fixtures/fake-dialogue-provider.ts` | 성공·오류·지연을 제어하는 테스트 전용 공급자 |

서버 인증, 방 접근 확인, 실제 공급자 선택, SDK 재시도 정책, 금액 예산과 UI 연결은 후속 작업 E·F에 남아 있습니다. 이 모듈을 그대로 공개 API로 노출하지 않습니다.

## 입력 경계

`buildDialogueContext`에는 권한 확인을 마친 내부 게임 상태를 전달합니다. 낮·투표 단계의 살아 있는 NPC만 발언 대상으로 허용합니다. 심문은 살아 있는 다른 참가자의 요청과 길이 제한을 통과한 질문이 있어야 합니다.

공급자 입력은 자신의 이름·역할·성격, 공개 참가자의 ID·이름·생존 상태, 최근 공개 대화와 질문으로 제한합니다. 다른 참가자의 역할·신뢰도·의심도, 전체 밤 행동·투표 맵, 저장 프로필을 포함하지 않습니다. 해당 NPC 자신의 조사 결과와 역할 안내를 포함한 모든 개인 로그도 모델 대화 입력에서 제외합니다.

- 공개 대화는 최근 12개, 각 본문은 최대 400자, 표시 이름은 최대 40자로 제한합니다.
- 심문 질문은 빈 내용을 거절하고 400자를 넘으면 거절합니다.
- 고정 지침과 사용자 질문·대화 데이터를 별도 필드로 전달합니다. 질문을 지침 문자열에 합치지 않습니다.
- 문자 제한은 JavaScript 문자열 길이 기준입니다. 실제 공급자의 토큰 한도는 E에서 별도로 설정합니다.

입력 분리와 기본 응답 검사만으로 모든 프롬프트 주입·역할 유출을 막는다고 보장하지 않습니다. 실제 모델 도입 전 한국어 대사·우회 표현·정보 노출 평가가 필요합니다.

## 요청 생명주기

`createDialogueCoordinator`는 게임 하나당 한 인스턴스로 만듭니다. 같은 게임에서 요청 ID는 재사용하지 않고, 동일 요청 재시도에만 같은 ID·문맥·대체 대사를 사용합니다.

1. `buildDialogueContext`로 입력을 만들고 무효 요청이면 중단합니다.
2. 기존 규칙 로직에서 대체 대사를 한 번 선택합니다.
3. `request({ requestId, context, fallback })`를 호출합니다.
4. 응답을 기다린 뒤 `claim(requestId)`가 반환한 결과만 메시지에 추가합니다.
5. 단계 변경·취소 시 `cancel(requestId)`, 게임 리셋·종료·연결 해제 시 `dispose()`를 호출합니다.

`request`는 동시 호출과 완료 후 재시도에도 같은 작업의 결과를 재사용합니다. 같은 ID에 다른 문맥이나 대체 대사를 보내면 `conflict`로 거절합니다. 요청 당시 입력과 대체 대사를 복사해 보관하며 공급자에는 별도 입력 복사본을 전달합니다.

`request`의 완료 결과를 직접 화면에 추가하면 호출자마다 중복 표시할 수 있습니다. 게시에는 반드시 `claim`을 사용합니다. 같은 ID의 결과는 한 번만 가져갈 수 있으며, 소비 시점에도 현재 단계인지 확인합니다. 완료 결과는 호출자가 바꾸지 못하도록 동결합니다.

## 제한과 결과

| 설정 | 기본값 | 의미 |
| --- | --- | --- |
| `timeoutMs` | 3000 | 공급자 응답을 기다리는 제한 시간 |
| `maxOutputChars` | 280 | 공급자 응답과 준비된 대체 대사의 길이 상한 |
| `maxRequests` | 40 | 게임 인스턴스에서 승인·보관하는 고유 요청 수 상한 |
| `isCurrent` | 필수 콜백 | 게임 ID·라운드·단계가 여전히 유효한지 판단 |

`isCurrent`는 변경 가능한 최신 상태를 읽어 판단해야 합니다. 요청 시작 전·응답 처리 시·게시 소비 시에 검사합니다. 단계가 바뀌면 호출자가 취소해 대기도 중단할 수 있고, 취소하지 않더라도 늦은 응답은 폐기합니다.

| 경우 | 결과 |
| --- | --- |
| 정상 공급자 응답 | `ready`, `source: provider` |
| 공급자 없음 | `ready`, 기존 대사와 `disabled` |
| 공급자 예외·시간 초과·잘못된 출력 | `ready`, 기존 대사와 정해진 오류 코드 |
| 취소·이전 단계·게임 폐기 | `discarded`, 메시지를 추가하지 않음 |
| 다른 게임·빈 ID·잘못된 요청 | `discarded`, 공급자를 호출하지 않음 |
| 요청 상한 초과 | `discarded`, `capacity`; 새 작업은 승인하지 않음 |

공급자의 원본 오류 메시지는 반환하지 않습니다. 응답은 `text` 문자열 하나만 가진 객체여야 하며, 빈 내용·장문·제어 문자·코드 블록·명시적인 역할 자백 패턴은 대체 대사로 바꿉니다. 이는 제한적인 형식·패턴 검사이며 의미 기반 검증을 대신하지 않습니다.

시간 초과·취소 시 `AbortSignal`을 중단합니다. 공급자가 이를 무시하더라도 조정기는 기다림을 끝내고 늦은 응답을 게시하지 않습니다. 이미 시작된 외부 호출의 비용까지 취소되는 것은 아니므로 실제 공급자 계약과 SDK 정책을 확인해야 합니다.

캐시에서 승인된 ID를 중간 삭제하지 않습니다. 삭제 후 재시도하면 중복 호출할 수 있기 때문입니다. 상한에 도달하면 새로운 ID를 거절하고, 종료 시 `dispose()`가 모든 보관 작업을 정리합니다. 상한 초과 후 규칙 기반 게임 흐름을 계속하는 정책은 UI 연결 단계에서 구현합니다.

이 중복 제어는 한 인스턴스의 메모리 범위입니다. 서버 재시작·다중 프로세스·다중 장비의 중복 방지 및 금액 예산은 서버 단계에서 추가합니다.

## 검증

Node 22에서 기존 테스트와 함께 실행합니다.

```bash
node --import tsx --test tests/*.test.ts
```

가짜 공급자로 정상·실패·동시 중복·완료 재시도·ID 충돌·입력 변경·잘못된 응답·시간 초과 후 지연 응답·취소·게임 폐기·단계 변경·상한·입력 정보 분리를 검증합니다. 실제 API나 브라우저 화면을 검사한 것은 아닙니다.
